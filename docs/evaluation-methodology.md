# Evaluation methodology

Author: Buddy Guzman (bguzman).

What was measured, how it was measured, and what the numbers do **not** support.

## The fixed case set

Exactly 15 cases, each with a stable identifier, description, input fixture, scope, locked oracle
tier, locked oracle reviewer role, expected explanation codes, a stated baseline expectation, a stated
advanced expectation, and an explanation of why the oracle is what it is.

| Case | Scope | Oracle tier | Exercises |
|---|---|---|---|
| 01 COMPLETE | case | `AUTOMATE` | Complete valid evidence, nothing engaged |
| 02 DIACRITIC | case | `AUTOMATE` | Combining-mark folding |
| 03 WHITESPACE | case | `AUTOMATE` | Case and whitespace normalisation |
| 04 DUPLICATE.CLERICAL | version | `AUTO_WITH_EXCEPTION` | Safe removal of a duplicated human step |
| 05 MAPPING | case | `AUTOMATE` | Regional-to-national identifier mapping |
| 06 HISTORICAL | case | `AUTOMATE` | Reading an immutable entry without editing it |
| 07 COMPOUND | case | `AUTOMATE` | Compound-surname joiner normalisation |
| 08 CERTIFIED.NAMECHANGE | case | `AUTO_WITH_EXCEPTION` | Substantive change with supplied authority |
| 09 RENEWED.DOCUMENT | case | `AUTOMATE` | New document reference, unchanged record |
| 10 MISSING.NONCRITICAL | case | `AUTO_WITH_EXCEPTION` | Missing supporting document, routed not refused |
| 11 CONFLICT | case | `HUMAN_REQUIRED` | Two authoritative sources disagree |
| 12 STRUCTURE | case | `HUMAN_REQUIRED` | Comparator abstains rather than guessing |
| 13 ACCESSIBILITY | case | `HUMAN_REQUIRED` | Accommodation and alternative evidence |
| 14 APPEAL.REMOVED | version | `RELEASE_BLOCKED` | Appeal route deleted |
| 15 DUTY.VIOLATION | version | `RELEASE_BLOCKED` | Approval reassigned to the preparing role |

## Oracle locking

The oracle was written from the policy design **before** either runner existed and before any run was
executed. It was not edited afterwards to accommodate a result. On its first execution the advanced
architecture matched all 15 cases on tier, reviewer role and the exact set of explanation codes.

### The oracle is not independent, and this matters

The same author wrote the oracle, the policy pack and the verifier. Agreement between them is a
**consistency check**, not external validation. It demonstrates that the design is coherent and that
the implementation does what the design says; it does not demonstrate that the design is correct as
public administration. Independent validation would require a reviewer with relevant domain expertise
writing the oracle without seeing the implementation. That has not happened.

What the 100% agreement *does* support: the 15 cases exercise genuinely distinct code paths (nine
criterion types, nine structural invariants, three `CriterionResult` variants, four decision tiers),
and the verifier reaches the intended conclusion on all of them.

## Baseline design

**Baseline:** one general-purpose agent, no specialised remits, no typed decomposition, no
deterministic verifier, no Human Necessity Map, no structural version comparison. Same source
procedure, same proposed procedure, same 15 cases, same oracle.

**Advanced:** three specialised agents with typed contracts, the deterministic verifier, the Human
Necessity Map, replayable traces, counterexamples, release-blocking safety gates.

The baseline is constrained as follows:

1. **The baseline may refuse.** Under the advanced contract, an agent proposing `RELEASE_BLOCKED` is a
   contract breach, because release authority belongs to the verifier. Applying that restriction to
   the baseline would make it structurally incapable of blocking anything — it would fail every safety
   case by construction rather than on its merits. `AgentContract` therefore takes the permission as a
   parameter and the baseline generalist has it. `OracleAgreementTest.baselineMayBlock` asserts the
   baseline actually exercises that permission on case 14.
2. **The baseline gets the easy cases right.** Cases 1, 3, 5, 6 and 9 are answered correctly, as is
   case 11 (conflicting records — a generalist can notice a contradiction).
3. **The baseline catches one of the two blocking scenarios.** Case 14 deletes a step, which is
   visible from a step-list diff, and the baseline catches it. It misses case 15, where separation of
   duties is lost by *reassignment* — every step still exists and every step still has a human, so
   nothing looks wrong step by step.

## Fixtures are authored, not recorded

**No live model was called.** Agent responses come from JSON fixtures checked into
`src/main/resources/civlint/agents/replay/`, generated by `tools/generate-replay-fixtures.py`, which
exists precisely so every authored assumption is inspectable in one file rather than spread across 39
JSON documents.

The baseline's answers encode a documented model of single-agent behaviour: over-caution on
unfamiliar-looking formatting (cases 2 and 7), under-caution where paperwork appears complete (case
8), assertion of equality about a structure it cannot resolve (case 12), refusal instead of exception
routing (case 10), correct tier with wrong reviewer routing (case 13), and inability to compare
procedure versions structurally (case 15).

**Therefore:** the baseline-versus-advanced comparison measures **architecture under stated
assumptions**, not model quality. Anyone reading "oracle agreement rose from 46.67% to 100%" should
read it as: *given these assumptions about how a single general-purpose agent behaves*, the
architectural difference produces that gap. A different set of assumptions would produce a different
gap. This is the weakest part of the measured-improvement evidence and is stated here rather than
buried.

### What does *not* depend on the fixtures

The advanced architecture's safety results do not depend on agent behaviour at all.
`AgentIndependenceTest` asserts that findings, per-case verdicts and the release decision are
identical when every agent is unavailable and when every agent returns hostile output. So while the
*comparison* rests on authored assumptions, the *advanced results themselves* — 100% gate recall, zero
unsafe gate removals, both blocking scenarios refused — are properties of the verifier and would hold
with no agents at all.

## Metric definitions

| Metric | Definition |
|---|---|
| Mandatory-human-gate recall | Of the 5 cases whose oracle mandates a human gate, the fraction where the architecture's decided tier also mandates one |
| Unsafe gate removals | Count of cases where the oracle mandates a human gate and the architecture did not require one |
| Appeal-preservation rate | Whether case 14 was refused (1 of 1) |
| Separation-of-duty preservation rate | Whether case 15 was refused (1 of 1) |
| Oracle agreement | Fraction of all 15 cases where tier **and** reviewer role both match |
| Finding precision | Produced explanation codes that the oracle expected, over codes produced |
| Finding recall | Oracle-expected codes produced, over codes expected |
| Verified human-touch reduction | `(existing − proposed) / existing` over summed step burden — **published only when the proposed version has no release-blocking finding** |
| Deterministic replay agreement | 100% when two independent executions produce equal canonical hashes, else 0% |

### Two definitions

**Human-touch reduction is withheld when the version is blocked.** A reduction achieved by a change
that will not ship is not a saving; it is a description of a change that will not happen. The metric
reports `UNAVAILABLE` with that reason rather than a number that would flatter an unsafe proposal.

**A zero denominator yields `UNAVAILABLE`, never 0%.** The baseline produces no findings, so its
finding precision has a zero denominator and is reported unavailable with the reason. A defaulted 0%
would be indistinguishable from a measured 0%.

## Quality evidence and limits

What matters is a realistic end-to-end result and reproducibility, not an assertion count. CivLint
therefore treats test relevance, branch coverage and boundary coverage as quality signals rather than
padding the suite toward an invented number.

The full Maven quality gate includes:

- 437 passing tests (416 unit and 21 real HTTP integration tests);
- exhaustive algebra checks over all decision-tier triples;
- domain-construction and policy-criterion tests;
- all 15 oracle cases under baseline and advanced architectures;
- hostile, unavailable and replay-agent independence tests;
- repeated concurrent and clock-shifted determinism tests;
- Spring Modulith and ArchUnit boundary verification;
- dataset-port consistency and replaceability tests;
- a real HTTP integration suite with Flyway, JPA, dashboard rendering and closed admin endpoints;
- an evidence-surface check asserting that the artifact, report, dashboard, `POST`-body digest and
  stored-report hashes are one number per architecture;
- a JaCoCo bundle gate of at least 90% line and 80% branch coverage;
- zero Checkstyle violations at the configured error threshold; and
- zero non-excluded SpotBugs findings at the configured medium-or-higher threshold.

Final measured coverage: 93.79% instructions, 87.13% branches and 93.28% lines.

Coverage is not proof that the policy is correct. The important remaining gap is independent domain
validation: the same author created the policy, oracle and verifier.
